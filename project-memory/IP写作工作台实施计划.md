## 1. 最终要做成什么

一个以 IP 为组织中心、以共同写文章为核心的本地应用。

用户提供思想、经历和零散表达。AI 像“写书人”一样，通过聊天引导用户补充内容，把内核整理成适合该 IP 和读者的文章。用户不需要先学会项目的数据结构，也不需要填完一套写作表格才能开始。

首页看全局；文章页完成一篇文章。聊天、当前母稿、修改建议、配图、排版及分发操作围绕同一篇文章展开，不要求用户在多个页面之间搬运内容。

关系如下：

```text
IP（赛道、读者、人设）
├─ 平台账号：小红书、公众号等；同平台允许多个账号
├─ 灵感与选题储备
└─ 文章母稿
   ├─ 对话与素材
   ├─ 当前正文与修改建议
   ├─ 配图
   └─ 各平台分发准备及实际发布记录
```

同一选题写给另一个 IP，可以建立另一篇母稿。同一 IP 的一篇母稿发到多个平台，不要求重新写一篇独立文章。

## 2. 用户已确认的规则

| 事项 | 已确认要求 |
|---|---|
| 管理中心 | 按 IP 划分，平台账号属于 IP；不能按平台分成互不相通的写作空间 |
| 建立 IP | 必须明确赛道和目标读者；语言风格、样例可以暂空，边写边形成 |
| 写作方式 | 自然聊天。AI 主动引导、追问缺失内容，不能要求用户先知道自己要什么 |
| 个人感悟 | 忠于用户感受、立场和表达意图，不替用户判定感受对错；涉及外部事实时仍须核实 |
| 教程和实战记 | 检查知识、步骤及事实，指出理解错误，不盲目附和；不能编造用户做过的操作和结果 |
| 人设表达 | 按 IP 和目标读者写；避免机械、官方语气。活泼、玩笑、白话是否合适，由具体 IP 决定 |
| 共同编辑 | 聊天与文章同时展示；用户可以直接编辑文章；AI 之后读到的必须是用户最新版本 |
| AI 写入 | 先展示拟写内容或修改建议，用户确认后才写入母稿。不能因用户聊天就自动覆盖正文 |
| 正文审核 | 用户确认正文没有问题，才进入配图 |
| 配图审核 | 图片出来并经用户确认，再进入排版与分发；不能只放占位框就算完成 |
| 多平台 | 共用母稿，尽量复用；平台必要差异放在分发准备中，变更正文须先展示并确认 |
| 首页 | 显示 IP、账号、平台数据；准备写、写一半、写好未发的文章；选题储备数量 |

“初版、中版”理解为同一篇文章的迭代，不额外设计强制填写的阶段。语言偏好可积累，但 AI 不得把一次临时修改自动保存为永久人设；如需保存，先展示并由用户确认。

## 3. 本轮不扩大到哪些事情

- 不重新开发实时语音或另一套聊天系统，沿用应用内模型 API 对话。
- 不更换技术栈，不引入 npm、pip、CDN、框架或数据库服务。
- 不把所有现有实体改名、合并成一个文件，也不先做全站视觉翻新。
- 不优先做抓数、复杂分析、抖音/B站适配或自动运营。
- 不编造账号数据、个人经历、测试结果和发布成功状态。
- 不改写 Git 历史，不提交私人数据、密钥，不自行推送远程。

“工作台内完成发布”的目标需要区分准备与平台实际提交。现有项目没有可用的自动发布能力。本轮先在文章页完成排版、复制或导出、打开发布入口，以及记录真实发布结果。实际提交暂由用户在平台完成；自动发布若要纳入后续开发，需要另行核实权限和取得用户确认。不能把复制成功显示成发布成功。

## 5. 分步计划表

按顺序推进。每一步先完成交付物和验收，再继续依赖它的步骤。不能用“代码写完”代替“体验已验收”。

| 步骤 | 做什么 | 做到什么程度才完成 | 主要交付物 |
|---|---|---|---|
| 1 | 明确首页、IP、文章页的结构和操作路径 | 用户看得懂从哪里开始、怎样聊天写稿、在哪里确认；先确认结构，再做大范围页面改动 | 页面结构草案、关键操作说明、用户反馈 |
| 2 | 确定最小数据契约和兼容方案 | IP、母稿、建议、审核、图片、分发各有明确存储；旧文件可读且不丢数据 | 数据契约增量、迁移与恢复说明 |
| 3 | 接好 IP 建立和写作上下文 | 仅有赛道和读者就能开始；正确隔离不同 IP，风格缺失不阻塞 | IP 入口、校验、上下文构建 |
| 4 | 完成文章与聊天的共同编辑 | 用户修改后 AI 读取最新版；建议先展示，确认后应用；旧建议不能覆盖新编辑 | 文章页核心原型、修订保护、对话存储 |
| 5 | 完成“写书人”引导与事实核验 | 两类文章走适合的对话方式，不编造经历；核验有依据，无能力时如实说明 | 提示规则、核验记录、真实文章试写 |
| 6 | 完成正文审核和真实配图 | 用户确认正文后开始配图；图片可保存、预览、替换并确认 | 审核记录、图片文件及关联 |
| 7 | 完成一母稿多平台排版与分发准备 | 不复制独立母稿也能准备小红书和公众号发布；各账号发布状态独立 | 平台排版、必要适配建议、发布记录 |
| 8 | 整理首页和导航，完成整体验收 | 新用户无需讲解能从首页进入 IP、完成一篇文章；状态和数量可信 | 完整体验、验证记录、更新后的交接文档 |

## 6. 第一步：先确认结构，不先堆功能

### 工作内容

1. 画出首页、IP 内容视图、文章页的简要布局。可以复用现有页面，不预先规定必须增加页面文件。
2. 首页以信息表为主：按 IP 展示账号与数据；展示准备写、正在写、正文已确认但未完成发布的文章；展示选题储备。缺少数据就显示空值，不用假数据撑版面。
3. 文章页保留稳定的正文区域和对话区域。正文始终能回到眼前，配图或排版操作不能让用户失去正在写的文章。
4. 区分“查看配图/排版”和“确认进入下一步”。看一眼页面不能修改业务阶段。
5. 首页保留清晰的开始写作入口；具体放在哪里、导航保留哪些项，由草案验证，不擅自铺开全站。

### 验收

- 用户能指出：在哪里选 IP、开始一篇文章、继续旧稿、看待发文章、看账号数据。
- 用户能理解母稿只有一篇，平台在后面选择。
- 用户确认结构后，把确认结果写入本计划的进度区，再开始大幅调整页面。

## 7. 第二步：先定存储和兼容，再改业务

### 工作内容

沿用已有六实体。界面使用“IP”，存储可继续使用 `身份` 和 `per-*`，避免无收益的批量改名。母稿继续使用现有 `稿件` 和 `dr-*`。

在现有契约上补足以下信息，具体字段名和文件路径在本步确定，后续统一使用：

| 信息 | 必须表达的内容 |
|---|---|
| IP | 赛道、目标读者必需；语言偏好、样例可选 |
| 母稿 | 所属 IP、文章类型、当前正文、当前修订标识 |
| AI 建议 | 建议内容、所基于的正文修订、待确认/已采用/已失效状态 |
| 审核 | 用户确认的正文修订；配图确认及其对应版本 |
| 图片 | 真实本地文件、用途及关联母稿；不能只有平台类型字段 |
| 分发准备 | 母稿、目标账号、排版参数、必要适配及其依据的母稿版本 |
| 实际发布 | 沿用投放记录；每个账号分别记录真实发布时间、链接和数据 |
| 对话 | 按稿件保存，刷新可恢复；归档不删除正文和素材 |

约束：frontmatter 解析只支持扁平字段，不能直接写嵌套数组。复杂信息选用明确的小节或独立本地文件；不能为了省事把平台版本、数据、人设全部塞进母稿正文。

迁移前在本地备份，只对测试副本验证。读取旧稿时给缺失的新字段合理默认值，但不能把旧稿自动认定为已审核。不能重建私人数据目录或覆盖已有正文。数据目录迁移的现有半成品不与产品重构混成一项验收：如要启用，单独验证路径、复制完整性和重启生效。

### 验收

- 旧 IP、账号、选题、稿件和投放仍可读取，原正文不变。
- 一篇母稿能关联两个账号；发布状态可以一边已发、一边待发。
- 明确哪些是已实现接口、哪些是待新增接口，不把设计表写成现有能力。
- 更新 `数据契约.md`，记录迁移及恢复方法后再写依赖它的功能。

## 8. 第三步：IP 是写作上下文的起点

### 工作内容

- 提供创建、选择和修改 IP 的清晰入口。新建时要求赛道、目标读者；名称作为基本识别信息。
- 语言风格和样例为空也允许进入写作，删除旧的风格硬门槛。
- AI 以稿件绑定的 IP 为准，不能因为侧栏切到另一个 IP 就把当前文章写串。
- IP 未明确时先补必需信息，不让模型猜读者和赛道。
- 后续风格调整通过用户认可逐步积累，不自行把文章事实当成永久人设。

### 验收

- 建一个只填名称、赛道、读者的 IP，可以开始聊天和生成建议。
- 两个 IP 使用相同素材时，上下文各自独立。
- 已有详细人设、写作样例和技能设置继续可用。

## 9. 第四步：先把共同写一篇文章做顺

### 工作内容

这是核心，优先于配图和发布能力。

1. 同屏显示当前母稿与聊天，用户可直接编辑正文；编辑有明确的保存状态。
2. 用户发送消息或请求 AI 修改前，先确保当前编辑内容已保存，或将当前完整版本及修订标识可靠传入。保存失败时不让 AI 假装读到了最新版。
3. AI 回答、拟写初稿和修改建议与正式正文分开；用户未确认时，正文不变。
4. 用户采用建议时校验基础修订。用户已改字、另一窗口已保存或正文版本变化时，阻止旧建议整篇覆盖，要求基于最新版重新生成。
5. 采用后两边读到同一个版本，旧稿有本地备份可恢复。初版、中版通过修订表达，不要求用户另开稿件。
6. 接通现有对话存储路由，刷新后恢复；处理失败提示和缓存恢复，避免声称“自动接上”却丢掉断线消息。
7. AI 建议只能影响其明确显示的文章与字段；用户确认的是哪份建议，落盘就必须是哪份内容。

### 验收场景

- 用户把第二段改成一句新话，接着问“你看我刚改的这段怎样”，AI 能基于新话回应。
- AI 展示建议后，用户再次改正文，旧建议无法静默覆盖新内容。
- 不点采用，刷新页面后正式正文仍未改变。
- 采用后只修改对应正文，不损坏素材、配图等其他小节；正文内的 Markdown 小标题完整保留。
- 刷新、重启后，已保存正文与对话仍在。换稿件不会混入另一篇对话。

## 10. 第五步：让 AI 像写书人一样引导

### 工作内容

- 结合已有素材提问，一轮问少量关键问题，不固定让用户填写冲突四格，不重复问已明确的内容。
- 对个人感悟，梳理用户真正想表达的判断、故事和情绪；资料不足先问，不编个人经历。
- 对教程和实战，区分用户亲历、外部事实和待验证判断。必要时展示纠错及依据，再形成文章建议。
- 信息足够就提出文章方向或初稿，用户确认采用；不以追问为目的无限聊天。
- 人设约束落实在输出里。允许白话、松弛和适合该 IP 的玩笑，不统一做成官方解说口吻。

### 核验能力的边界

目前应用里的模型对话不等于具备联网检索。不能仅加一句“请核验”就声称事实已验证。

本步先核对代码是否具备可靠的资料读取能力。没有时，允许用户提供官方文档、原文或测试结果；引用记录须能追溯。链接读取失败、来源不足或只能凭模型记忆时，明确记为待核实，不能标“核验通过”。如需要新增在线检索服务，先给出能力范围、配置及费用要求，由用户确认后再接入。开发助手在外部做过检索，不代表应用内获得相同能力。

### 验收

- 用一篇个人感悟和一篇教程/实战进行真实试写，由用户判断是否表达了自己的内核、是否符合 IP。
- 对有明确资料证明的错误，能指出问题并给出可追溯依据。
- 不确定的事实不伪装为结论；无来源时不编链接、引文和实测结果。
- “像不像我、读起来是否愿意读下去”必须由用户验收，不能用模拟模型或自动测试替代。

## 11. 第六步：正文确认后配图

### 工作内容

- 用户明确确认正文，记录确认所对应的版本，再进入配图工作。
- 图像文件保存在本地并关联母稿，支持预览和替换；图片建议也先展示，不直接假定用户接受。
- 真实出图方式在本步核对：能接现有生成能力就明确配置；没有时先支持导入用户提供的图片，不把上传入口称作 AI 自动出图。
- 平台封面或比例有不同需求时，作为母稿下的图片用途或衍生结果管理，不拆成两篇文章。
- 用户确认图片后才进入排版。允许明确选择不配图，但不能用默认跳过代替用户决定。
- 正文修改后，原确认失效；旧图片保留，提示需要复核，由用户决定继续用或替换，不自动清空。

### 验收

- 真实图片可保存，重启后仍能预览，不只显示占位框。
- 未确认正文时不能被 AI 自动推进；未确认图片时不能自动认定排版已就绪。
- 改正文不会删除已做图片，但不会继续显示旧审核有效。

## 12. 第七步：母稿不分裂，平台结果分别管理

### 工作内容

- 首先覆盖小红书、公众号。同 IP 下选择对应账号，复用同一篇母稿和图片。
- 先处理标题、封面、图片尺寸、排版和平台必要格式，不默认给每个平台重写全文。
- 若遇到平台实际限制，清楚说明限制及建议，用户确认后保存平台适配结果。不能偷偷改变母稿立场或反向覆盖母稿。
- 平台适配记录绑定母稿修订。母稿修改后提示旧适配需复核，不无提示地继续发布旧稿。
- 在文章页完成预览、复制或导出、打开平台入口，以及录入发布结果。诚实区分“准备完成”和“实际已发布”。
- 某账号已发布不代表整篇文章向所有目标账号都已发布。

### 验收

- 同一篇母稿可准备两个平台，不需要建立第二篇独立母稿。
- 两个平台的必要格式调整互不影响，母稿正文保持用户确认的版本。
- 小红书已发、公众号未发时，两种状态均正确显示，首页仍能找到待发项。
- 复制或导出失败不记为已发布；实际记录关联正确 IP、稿件和账号。

## 13. 第八步：收拢首页和完整体验

首页结构已在第一步确认；本步使用真实业务状态接入和收尾。

- 按 IP 组织账号、平台及已有数据，提供全局总览和清晰的 IP 入口；不强制先选某个平台才能写。
- 用用户能理解的词展示准备写、正在写、正文已确认及待分发内容，计数从文件计算。
- 明确选题储备的计算口径，避免已用、废弃和已有稿件被重复当成待写储备。
- 待发数量区分文章数与账号分发数。例如 1 篇母稿还有 2 个账号未发，不能含混地写“2 篇”。
- 首页没有内容时告诉用户可以从哪里开始，不堆空卡片；每条信息能进对应对象。
- 简化导航及附属信息，把底层实体 ID、数据契约和技术说明从日常创作主视图收起。
- 桌面验证聊天和文章同时可用；窄屏保证可编辑、不溢出，并能方便切换聊天与文章。

### 最终验收脚本

1. 新用户建立 IP，只填名称、赛道、读者。
2. 说一段零散想法，AI 根据缺口引导补充。
3. AI 展示拟稿，用户确认后进入当前母稿。
4. 用户直接改正文，再聊天；AI 读到用户改过的版本。
5. AI 提供修改建议，用户确认应用；旧建议不会覆盖新编辑。
6. 用户确认正文，完成真实配图，再确认图片。
7. 同页为小红书与公众号准备排版和分发，复用母稿。
8. 记录一个账号已发布，另一个仍待发；首页正确反映。
9. 刷新并重启，IP、正文、对话、图片及分发状态保留。
10. 另外用教程/实战测试事实纠错；无核验能力的部分清楚显示待核实。

验收必须同时满足：功能走通、数据不丢、用户认为逻辑清楚且文章表达符合 IP。任何一项未满足，写明未完成部分。

## 14. 验证和交接规则

### 开工前

1. 读 AGENTS.md → INDEX.md → STATUS.md → 本计划，只读当前步骤需要的专题。
2. 看 `git status` 和当前提交，保护未提交修改。本文记录的提交只是起点，不假定后续工作区没变化。
3. 每次明确本轮做哪一步、修改范围和验收场景。不要一次重写所有页面。

### 每步结束

- 检查相关 Python/JavaScript 语法；对数据写入、修订冲突、审核和跨 IP 隔离跑必要测试。
- 用本机模拟模型验证协议和异常处理；真实写作质量另用实际模型及用户素材验收。
- 页面改动做浏览器检查，不只读源码判断布局。通过后仅在相关改动或新疑点出现时重跑。
- 权限导致测试无法执行时，记录具体阻塞；不能把权限错误计为功能失败，也不能写“测试通过”。
- 更新 STATUS.md 和本文进度表，写明完成项、证据、未完成项、下一步；接口或行为变了同步更新专题。
- 实施过程中遇到与已确认目标有关的新分歧，先做可审阅草案再请用户决定，不自行换产品方向。
- 本地提交按用户授权执行；推送、真实发布和历史改写不在本计划的自动授权范围内。
